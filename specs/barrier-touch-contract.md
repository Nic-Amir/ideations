# barrier-touch-contract Specification

## Purpose

Defines the Barrier Touch contract lifecycle: dual mode selection
(`count` / `sequence`), count-bucket and sequence-pick resolution,
the status machine (`OPEN` → `{WON, LOST, REFUNDED}`), parameter
locking, path generation and audit replay, duration and stake bounds,
the one-active-contract constraint, and the backend-owned trading
principle. Probability and payout maths are delegated to
`barrier-touch-pricing`; money movement to `barrier-touch-settlement`.

Barrier Touch is a touch-event product on one driftless GBM asset. In
**count** mode the player predicts how many times price crosses the
entry line within `T` ticks (buckets 0 / 1 / 2 / 3+). In **sequence**
mode the player predicts an ordered round trip across log-symmetric
barriers (Upper→Lower or Lower→Upper). Exactly one count bucket wins
every count round. An incomplete or wrong-first sequence is **LOST**,
not refunded — unlike `barrier-predictor-contract` where no-touch is a
first-class refund.

Both modes share one capability pair via `parameters.mode`. The path is
generated by the backend from a CSPRNG seed at `/buy`; reveal is a
replay. There is no mid-round cash-out.

## Requirements
### Requirement: Mode and Selection

A Barrier Touch contract SHALL carry `parameters.mode` ∈ `{count, sequence}` and a mode-specific selection:

**Count mode**

- Selection `parameters.bucket` ∈ `{0, 1, 2, 3}` where `3` means **3 or more** crossings.
- Wins iff the realised crossing bucket equals the pick.

**Sequence mode**

- Selection `parameters.sequence_pick` ∈ `{upper_lower, lower_upper}`:
  - `upper_lower` — Upper touched first, then Lower afterward within `T`
  - `lower_upper` — Lower touched first, then Upper afterward within `T`
- Wins iff that full sequence completes within `T`.

Mode and selection are locked at placement. A placement with mismatched fields (e.g. `mode = count` with a sequence pick only) is rejected as `invalid_selection`.

#### Scenario: Count bucket 2 wins

- **WHEN** `mode = count`, `bucket = 2`, and the path realises exactly 2 entry-line crossings within `T`
- **THEN** the contract is WON and the player receives the locked `potential_payout` for bucket 2

#### Scenario: Count wrong bucket loses

- **WHEN** `mode = count`, `bucket = 0`, and the path realises 3+ crossings
- **THEN** the contract is LOST and the player receives nothing

#### Scenario: Sequence Upper→Lower completes

- **WHEN** `mode = sequence`, `sequence_pick = upper_lower`, and the path touches Upper first then Lower within `T`
- **THEN** the contract is WON

#### Scenario: Sequence incomplete loses

- **WHEN** `mode = sequence` and the required second barrier is never touched by tick `T`
- **THEN** the contract is LOST (not REFUNDED)

#### Scenario: Sequence wrong first barrier loses

- **WHEN** `mode = sequence`, `sequence_pick = upper_lower`, and Lower is touched before Upper
- **THEN** the contract is LOST at the first-touch tick

### Requirement: Count Resolution

A **crossing** is two consecutive tick prices on opposite sides of `entry_spot`. Rules:

1. Tick index 0 is the entry spot (on the line). Tick 1 establishes the initial side (above or below); it is never itself a crossing.
2. A later tick that lands **exactly** on `entry_spot` keeps the previous side (no flip, no crossing).
3. Crossing count saturates into buckets via `bucket = min(count, 3)`.
4. Settlement is always at maturity `T`: `settle_tick_index = T`.

#### Scenario: Exact on-line keeps side

- **WHEN** the walk is above the line and a later tick equals `entry_spot` exactly
- **THEN** the side remains above
- **AND** that tick is not counted as a crossing

#### Scenario: Count always settles at T

- **WHEN** a count contract resolves
- **THEN** `settle_tick_index = tick_duration`

### Requirement: Sequence Resolution

Barriers are log-symmetric: `U = S₀ × exp(+d)`, `L = S₀ × exp(−d)`. After each tick `t = 1 … T`:

1. Inclusive touch: `price ≥ U` (upper) or `price ≤ L` (lower), 1e-8 precision.
2. Upper is checked before lower on the same tick.
3. First touch enters a "waiting for opposite" stage; the opposite barrier must be touched on a **strictly later** tick.
4. Wrong first barrier → LOST at `first_touch_tick`.
5. Correct first but no second by `T` → LOST at `T` (incomplete).
6. Full sequence → WON at `completion_tick`.

Discrete monitoring only — no continuous-time barrier watching.

#### Scenario: Exact barrier touch counts

- **WHEN** price equals `U` within 1e-8
- **THEN** Upper has been touched

#### Scenario: Second leg requires a later tick

- **WHEN** Upper is touched at tick 4
- **THEN** Lower on the same tick 4 does not complete Upper→Lower
- **AND** completion requires Lower on some tick `> 4`

#### Scenario: Settle tick on early bust

- **WHEN** the wrong barrier is first touched at tick 3
- **THEN** `settle_tick_index = 3` and status is LOST

### Requirement: Contract Lifecycle

1. `OPEN` — from `/buy` until terminal. Path generated at acceptance; reveal progresses tick by tick. Sub-states via `reveal_start_at`.
2. Terminal: `WON`, `LOST`, or `REFUNDED`.

Status enum `{OPEN, WON, LOST, REFUNDED}`. `settle_reason` for REFUNDED is `"operator_refund"` only — there is no `no_touch` / incomplete refund reason.

Restart recovery replays `(seed, locked parameters)` and settles to the determined outcome; no process-lifecycle refund.

#### Scenario: Reveal begins while OPEN

- **WHEN** the reveal stream emits the first post-entry tick
- **THEN** `reveal_start_at` is set and status stays OPEN

#### Scenario: Incomplete is not a refund

- **WHEN** a sequence contract reaches `T` without completing the pick
- **THEN** status is LOST
- **AND** `settle_reason` is not a refund reason
- **AND** no REFUND ledger row is written

#### Scenario: Operator refund only operational path

- **WHEN** an operator voids an OPEN contract
- **THEN** status is REFUNDED with `settle_reason = "operator_refund"`
- **AND** stake is credited back

### Requirement: Contract Timestamps

| Field | Meaning | NULL when |
|---|---|---|
| `start_time` | `/buy` accept instant | never |
| `tick_duration` | T | never |
| `reveal_start_at` | First reveal tick instant | awaiting reveal; early operator refund |
| `settle_tick_index` | Tick index when outcome known | early operator refund |
| `settle_tick_at` | Wall-clock settlement | non-terminal; early operator refund |

For count WON/LOST: `settle_tick_index = T`. For sequence: completion tick, bust tick, or `T`.

#### Scenario: Count settle index equals T

- **WHEN** a count contract with `T = 15` settles
- **THEN** `settle_tick_index = 15`

#### Scenario: Sequence win settle index is completion tick

- **WHEN** Upper→Lower completes at tick 8
- **THEN** `settle_tick_index = 8`

### Requirement: Parameter Locking

Locked at `start_time`:

| Parameter | Modes |
|---|---|
| `mode`, selection (`bucket` or `sequence_pick`) | both |
| `entry_spot` S₀ | both |
| `tick_duration` T | both |
| `instrument`, `volatility` σ | both |
| `commission_rate` c | both |
| `barrier_offset` d, `upper_barrier`, `lower_barrier`, `distance_factor` | sequence |
| `offered_odds` / per-bucket odds | both |
| `config_version` | both |

Admin σ/c changes MUST NOT re-price OPEN contracts.

#### Scenario: Barriers quotable on sequence buy

- **WHEN** a sequence placement is accepted
- **THEN** the response includes `entry_spot`, `upper_barrier`, `lower_barrier`
- **AND** `U × L = S₀²` within decimal precision

#### Scenario: Count buy has no corridor barriers

- **WHEN** a count placement is accepted
- **THEN** sequence barrier fields are null / omitted
- **AND** `entry_spot` is present as the crossing line

### Requirement: Path Generation and Auditability

At `/buy`, the backend MUST generate the tick path with driftless GBM:

```
S_t = S_{t−1} × exp(−½ σ² dt + σ √dt × Z_t)
```

`dt = 1/(365×24×3600)`, `Z_t ~ N(0,1)` from a CSPRNG. Seed persisted admin-only while OPEN. `(seed, locked params)` MUST replay prices and outcome bit-for-bit.

Count paths always have length `T+1` (index 0 = entry). Sequence generation MAY persist the full series through `T` for audit even when settlement is earlier; reveal MUST NOT expose ticks beyond the reveal position, and MUST NOT expose seed/outcome while OPEN.

#### Scenario: Path before buy response

- **WHEN** `/buy` is accepted
- **THEN** path, outcome, and settle tick are determined before the HTTP response is written

#### Scenario: Seed hidden while OPEN

- **WHEN** a player reads an OPEN contract
- **THEN** the seed and unrevealed ticks are absent

### Requirement: Duration Bounds

`tick_duration` MUST be an integer in `{10, 15, 20}` (default `15` when omitted). Other values rejected as `invalid_duration`.

#### Scenario: Default duration 15

- **WHEN** duration is omitted
- **THEN** `tick_duration = 15`

#### Scenario: T = 5 rejected

- **WHEN** `tick_duration = 5`
- **THEN** the placement is rejected with `INVALID_DURATION`

### Requirement: Barrier Offset Bounds

Sequence-only. Default `d` is auto-calibrated by `barrier-touch-pricing` so Standard `P(complete) ≈ 0.25` per direction. Distance factors Near `0.75` / Standard `1.0` / Far `1.4` scale the calibrated offset. Non-positive `d` rejected with `unsupported_barrier_offset`.

#### Scenario: Standard sequence default

- **WHEN** sequence placement on V_100, `T = 15`, Standard distance
- **THEN** locked completion probability per side is approximately `0.25`
- **AND** offered odds are approximately `3.88`

### Requirement: Stake Bounds

6dp USDT string in `[min_stake, max_stake]`; `buy_price = stake`; decimal-safe only. Max payout gate via `barrier-touch-risk`.

#### Scenario: Stake stored verbatim

- **WHEN** `stake = "10.000000"` is accepted
- **THEN** `buy_price = 10.000000` and PLAY_DEBIT is `-10.000000`

### Requirement: One Active Contract Per Account

At most one non-terminal Barrier Touch contract per account; reject with `trade_in_progress`.

#### Scenario: Concurrent rejected

- **WHEN** an OPEN touch contract exists and another placement arrives
- **THEN** it is rejected with `trade_in_progress`

### Requirement: Backend-Owned Trading Logic

Contracts only via `POST /api/barrier-touch/buy`. Path, outcome, and balances owned by the backend. No client path generation for money. Identical for ACC-/DEMO-. No cash-out endpoint.

#### Scenario: No client bypass

- **WHEN** the frontend places a trade
- **THEN** no local code path decides WON/LOST or moves balance without a backend response

#### Scenario: Unrevealed path not readable

- **WHEN** reveal is at tick 3 of a round settling at tick 9
- **THEN** ticks 4–9, seed, and outcome are not on player surfaces
